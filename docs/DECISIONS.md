# Decisions log

Owned by the integrator (the main Claude session). The owner approves. Worker threads never edit this file directly; they request changes in their handoff note.

Three kinds of entry, kept apart as the brief requires:

- **Approved**: the owner signed off. Treat as direction.
- **Proposed**: an implementation choice in use until the owner vetoes or a result contradicts it. Build against it, but keep it easy to change.
- **Demonstrated**: something the running build or a test has actually shown. Cite the test, playtest or commit.

The owner's own direction lives in [CREATIVE_BRIEF.md](CREATIVE_BRIEF.md) and outranks everything here.

| A5 | **Carried knowledge helps but never makes the rest of the game easy.** Data and adopted rules improve the model; they never replace measuring and engineering in a new encounter. How: (1) every encounter adds an unknown that carried knowledge does not cover (a new body's mass, a local effect, a changed ship); (2) the model forecasts, never plans (P6); (3) a forecast needs fresh tracking, which costs power, pointing and recording (P12); (4) the ship wears, and ship calibrations loosen with time, use and damage, so old numbers must be re-earned; (5) a validated rule earns its tighter envelope only within the range it was tested on (asteroid fixes that the passing held-out test fits count: the law was tested at their distances; integrator reading, owner may revise). **Specified by 1G (revision 2, merged):** (4) each ship calibration loosens as a random walk on the ship's own clock, by ship time, use and drops in reported condition, and must be re-earned by a fresh calibration (spec §3.7; rates are play values); (5) each passing held-out test records the distance span it covered per body, and outside those spans the default hedge stays (spec §7.4). **Owner (2026-11-14): every body.** A rule shared by all bodies (the distance law) applies its validated spans around every body, in this and later encounters (`validatedRange.transfer = shared-law`); a rule about one body or region applies only there. A new body's mass and calibration still have to be measured. Check: the 3E harness flies each encounter with carried knowledge and no new measurements, and that should not succeed comfortably. | 2026-11-14 |
| A6 | **Gravity assists are part of the game.** Real missions borrow speed and change direction by flying close past a moving planet. The same works under the game's law: the energy comes from the body's orbital motion (in the Gravity range, Beta moves 31.6 m/s around the barycentre; 1B derivation, Jacobi constant). Reaching the game's second stage takes a slingshot. The player plans and the model forecasts (P6): until the model has evidence at the flyby's distances, the forecast widens and ends before closest approach (1G spec §8.4), so a slingshot can be flown with confidence only after the law has been learned and checked there; a blind try is allowed and usually misses. Close passes are where the law departs most from Newton: past Beta at 300 km and 40 m/s, the ship turns about 220° where Newton predicts about 114° (confirmed by 2F's study, `docs/handoffs/2F.md`). Very slow, close passes can whip the ship more than once around the body, so gates need approach speeds that keep the pass flyable. Tracked asteroids are the safe way to probe the law at flyby distances (1G spec §10). Placement: **the Gravity range's exit is a slingshot past Beta through an asteroid belt that orbits Beta** (owner, 2026-11-14). The rocks move under the same law, so until the law is learned the model mispredicts them as well as the ship. Tracking them is how the player both dodges them and probes the law, and the model helps once failed runs have gathered data (A9). The P15 review places later stage gates. | 2026-11-14 |

| P1 | **Planar flight, 3D presentation.** Positions, velocities and attitude (one yaw angle and rate) live in one plane. The 3D view shows everything, including structures that extend above and below the plane (lattice strands, well funnels). Physics code uses 2D vectors behind a small vector module so a later move to 3D is a code change, not a rewrite. | Superseded by A11 (owner, 2026-11-14) |
| P2 | **Deterministic fixed-step simulation**, pure TypeScript, seeded random streams, headless tests. Same start state + same command sequence = identical result. Required for honest comparisons and procedure replay. | In use |
| P3 | **Stack:** Vite, TypeScript (strict), React for the console, Three.js for the 3D view, Vitest, static hosting. Pinned exact versions, each at least two weeks old when installed: Vite 8.3.5, React 19.3.1, Three 0.187.0, TypeScript 6.0.3 (typescript-eslint does not support TypeScript 7 yet), Vitest 5.0.5, ESLint 10.14.0. Node 22.12 or later. | In use |
| P4 | **Gravity normalization:** a = (GM / r₀²)(r₀ / r)^2.5, matching Newtonian gravity at a reference radius r₀. Clarified by 1B: **one shared, fixed r₀ for every body** (a per-body r₀ would make forces between bodies unequal); truth stores GM (m³/s²) and r₀, and K = GM·√r₀ (m^3.5 s⁻²). Bodies are point sources; radii are collision envelopes only, no softening. Consequences for a near-circular orbit around an isolated body: periapsis advances 149.12° per radial cycle; escape speed = 1.1547 × circular (Newtonian: 1.414). The ship's model may fit K or GM at the same r₀. | In use. Mathematics reference-checked by 1B's generator and independently implemented by 2A (D3) |
| P5 | **Predictive model split:** the model updates *numbers* (masses, thruster calibration, sensor biases) automatically from data the player collects, and is confident only where data exists. It never invents a new *rule*. When its structure is wrong, the evidence shows it (residuals that won't shrink, a fitted mass that drifts with distance). The player enables a model extension; the model fits it from retained data; Black Box tests it against a held-out attempt. A correct rule extrapolates to unsampled places; a wrong one visibly fails. 1G's specification (`docs/model/estimator-spec.md`) builds this with an automatic **per-distance gravity calibration**: per body, a table of measured gravity strength at the distances the ship has flown. It is numbers, not a rule, so it cannot extrapolate; outside sampled distances the forecast widens and then ends. | **Approved by the owner** (A4) |
| P6 | **The model forecasts; it does not plan.** It shows the consequences of the player's plan with an honest uncertainty envelope. Configuration, power allocation, burn timing and flying stay with the player. Things the ship has not sensed are absent from the forecast. | In use |
| P7 | **Measurement realism:** accelerometers sense only non-gravitational acceleration (thrust). Gravity is inferred from tracking (optical navigation fixes), whose quality depends on sensor power, pointing, range and equipment condition. | In use |
| P8 | **Recurrence contract:** triggered by loss of the ship or a voluntary Recall from the console. The whole expedition restarts from its beginning (A9): all physical state resets to the first arrival condition (position, velocity, propellant, charge, heat, damage, configuration defaults), and every encounter world (bodies and asteroids) to its definition, with starting geometry set by the run's seed (A10; answers 1G's open question 2). Black Box keeps: every record (telemetry, measurements, commands, configurations, issued forecasts), adopted model extensions, saved procedures and the chart of leads. The predictive model is rebuilt from Black Box data, so it carries over. Data up to the moment of loss is kept. The model sees only measurements Black Box recorded (1G). | In use; owner may revise |
| P9 | **Saved procedures:** a command sequence that worked can be saved and replayed. It replays exactly only when conditions match; different arrival state means the player adapts it. This is how familiar passages get faster without their rules changing. | In use |
| P10 | **Display semantics:** the dotted line is the *issued forecast* path of the centre of mass, frozen when issued. The solid trail is the measured path. Body axis and thrust direction are short ticks on the ship. The uncertainty envelope widens where the model is extrapolating, and the line ends at a horizon (where the 1σ envelope exceeds 10% of the distance to the nearest body, a play value) instead of widening without limit (1G). | In use; visual thread 1E may refine |
| P11 | **Truth/belief boundary:** the simulation's truth world and the ship's believed world are separate types (`src/contracts/truth/` vs `src/contracts/index.ts`). `src/model/`, `src/blackbox/`, `src/console/`, `src/view3d/` and `src/theme/` may not import truth or `src/sim/` (enforced by lint). The game layer (`src/game/`) is the only code holding both; it turns truth into measurements, sensed events and the view snapshot. Forecasts can only use what the ship has measured or assumed. | In use |
| P12 | **Data as a resource:** Black Box recording rate and sensor processing cost power (and storage); this maps to the challenge's "data" resource. | In use |
| P13 | **Contract conventions:** SI units throughout; body frame +x is the direction the main engine pushes the ship; model parameters and truth's hidden values share dotted IDs (`body.alpha.mu`, `thruster.main-engine.scale`); ship housekeeping reaches the model as telemetry measurements, not as direct state; the ship-systems step carries its seeded noise states in its own state, so it is a pure function and replays exactly; equipment protection trips are tracked separately from permanent condition; lattice exposure uses the fictional lattice unit, not a radiation dose (1C). Details in `src/contracts/README.md`. | In use |
| P14 | **Ship baseline (1C proposal):** four crew; 30.4 t wet, 24 t operational dry; 24 kN main engine at 320 s (≈ 690 m/s ideal Δv main-only); RCS; optional NEXT-scale ion engine; solar arrays (zero output until irradiance is measured), fuel cells and batteries on separately protected buses; pumped thermal loops and deployable radiators; 42 equipment assemblies in `data/ship-baseline.json`. Every rating is [ASSUMED]; mechanisms are sourced. **Owner review (2026-11-14), item 1 of 6:** crew of **one**: the player, who makes every call; no other crew. Mass ≈ 30.4 t, hull layout and RCS design approved. Life support keeps a fixed power and heat demand (and its spare air train), but its consumables never run out: no oxygen clock, so mission time is not a stressor through life support. **Item 2:** one propellant load per run (≈ 690 m/s main, ≈ 20 m/s RCS); nothing refills between encounters; recurrence restarts with full tanks. The amount is a tuning value: set it so that a scripted expert run (3E harness) reaches home with a margin. | **Owner review in progress; pending data-file change from 2F: the camera's 5% range figure is doubt about a body's size (one shared scale error), not per-fix noise, and applied per fix it makes the model's fit run away; split it into per-fix noise and a size bias** (items 3–6 pending); 2B builds against it meanwhile |
